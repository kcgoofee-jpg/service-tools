## 1. 防封号（最高优先级）

### 已修（已上线）

| 问题 | 影响 | 修法 |
|---|---|---|
| `parse_retry_after` 只认纯数字，HTTP 日期一律退化成 20 秒 | Cloudflare / WAF 用日期格式时，会在真实限流窗口内提前重试 → 升级封控的最佳入口 | 支持 RFC 7231 日期（过去→下限 5s，未来→按差值，上限 1h）；超长数字按「很长冷却」钳到上限 |
| 403 退避档位被一次成功清零 | 间歇性 403（WAF 抽检）时账号被以每 5 分钟一次的固定节奏持续试探 | `mark_ok` 只清连续计数；档位改由「24 小时内没有 403」衰减（`forbidden_last`） |
| 文本 / 语音 403 / 429 **完全静默**（无冷却、无告警、无 Token 健康记录） | 上游开始限流时，客户端以每 Key RPM 持续重试；文本 403 是账号级信号却没人知道 | 429 → 记 `fails` + 文本通道单独冷却（取 Retry-After）；403 → 连续 3 次告警；**不冻结生图**（保持原设计） |
| Anlas 订阅查询临时新建 httpx 客户端 | 配了 `UPSTREAM_PROXY` 时，同一把 Token 同时从代理 IP 和服务器 IP 出现 | 复用网关共享 client（继承代理）+ 15 分钟结果缓存 |
| 维护 / 算法循环精确 300s / 600s 网格 | 「每 600.0 秒一次订阅查询」是最容易被识别的机器节拍 | ±20% 抖动（`background_tasks.jittered`） |
| `daily_cap_fallback`(1500) > `account_daily_cap`(1000) 默认值 | 「上游 429/403 → 自动退档」保险丝**静默失效**（`old <= safe` 直接跳过） | 默认改 800 + `fallback_effective()`，后台模块页新增校验 |
| 单账号并发默认允许 2～4（`single_slot_enforced=False`） | 一次后台误操作就能让同一账号并发出多张（共享代挂特征） | 默认改强制 1（生产 DB 无覆盖值，实际行为不变，只堵住将来） |
| 无 body 的 GET 带 `Content-Type: application/json` | 与官方前端不一致的现成指纹差异 | 按方法决定是否带（`_headers(..., method=)`） |

### 未改（需要站长点头 / 属产品取舍）

1. **文本 / 语音没有账号级每小时上限**：目前只有每 Key RPM + 文本内部信号量。跨过 429 冷却后仍能持续打上游。建议给它接一条账号级串行或独立 RPM（属频率策略，改动需要站长确认）。
2. **`UPSTREAM_TLS_IMPERSONATE`**（在飞的 `feat/tls-impersonate`）：TLS(JA3/JA4) 仍是 Python/OpenSSL 原生指纹，属已知差异；合并该分支时按 §5 的解法处理。
3. **多账号并发窗口**：图片 lane 不占 `global_sem`，文本与图片可同时打上游；单账号生产实际是 1 并发，但两路同时出现时是 2 个连接（低频，量级小）。
4. **建议-tags 不计入 guard 每小时 / 每日上限**（只受 15 秒间隔约束）：量很小（近 3 天 84 次），未改，避免误伤成员补全。

## 2. 计算 / 分配 / 配对 / 性能算法

### 已修

- **注水桶三个数收敛成一个**：常量收口 `policy.FREE_BURST / FREE_REFILL_PER_HOUR / free_paced_cap()`。首页文案抽成可单测的 `quota_algo.quota_notice()`：
  以前写「蓄水池 A 张，每小时恢复 4 张，全天上限 **96** 张」，判定实际是 30 底仓 + 4/小时（全天最多 **126** 张），成员按页面理解必然误判。
  线上文案现在是：「今日额度：V4.5 每人 91 张/天（次日 0 点恢复） · V5 每人 10 张（全站今日共 260 张，先到先得）」。
- **V5 超卖可见 + 交叉校验**：`v5.oversell` 写进状态，`modules.allocation` 新增「每人额度 × 人数 ≤ 全站上限」，实测线上 1390 > 260 会标红并写 Bug 追踪。
- **每日复盘新增 `paced_blocks` 与 `budget`**：前者记录「被注水桶拦下」的次数（A 被虚高的证据），后者是拥挤度分母（账号日上限 − 全站 V5）。**只记录，不参与每日微调**。
- **自动驾驶名额判据**：拥挤度分母改用 `review.budget`，不再把 V5 用量算两次（同一批 V5 原先会连带冻结名额增长）。
- **风险检查「用量集中度」分母从 Top-6 之和改为全站总量**：47 人时会把正常重度成员误报「占全站 60%」。
- 另修：面板「Key 有效天数」读错属性名（永远显示 30）；新增「保底 ≤ 每日上限」校验。

### 未改（额度结果变更，留给站长）

1. **V5 每人额度 × 人数 > 全站上限**（线上实测 1390 vs 260）：现在只是如实说明「先到先得」。真要修：`each = min(each, global // 启用人数)`，或把分母从「最近 3 天用过 V5 的人数」改成「当天启用且 V5 额度 > 0 的 Key 数」。
2. **`water_fill` 分母按 Key 不按人**：开 10 把小号每人各出 1 张 → 分母 47→57，人均被稀释约 20%（`alt_guard` 只观察）。修法：先按 `discord_id` / 网段归并再 water_fill，并把「昨天 ≤3 张」的 Key 排除出分母。
3. **V4.5 上限 A > 126 时成员实际到不了 A**（注水桶封顶 126）：`paced_blocks` 已经把这件事量化，是否把桶改成 `4 → max(4, (A−30)/24)` 由站长定。
4. **`quota_algo` 每 10 分钟覆盖站长手改的 `global_daily_v5` / `register_*`**：后台已经禁用这些输入并说明「由算法管理」，但算法本身仍会无条件写。若希望人工值优先，需要加「人工覆盖」标记位。
5. **DRR 公平调度仍只观察**（FIFO 实跑）；`lab/replay` 的校准模型缺「每人注水桶」这一层，回放出的失败率偏低——建议补进回放再谈是否开 DRR。

## 3. 冲突代码与功能冲突

### 已修

- **落地页 JS 找的 6 个元素在页面上根本不存在**（`algoNote` / `audit` / `auditTxt` / `pills` / `liveTitle` / `headKey`）→ 今日额度说明、**数据记录披露**、名额胶囊、打码 Key 全都不渲染。已补回（线上验证 5/5 存在）。
- **全站上限缺值时写死 1700 / 260** → 改为缺值显示「不限」。
- **新建 Key 表单 V5 默认 0（=不限），后端默认 50，注册默认 3** → 表单默认值改为与「新成员默认额度」一致。
- **公告预览 `innerHTML` 直插**（后台 CSP 允许内联脚本）→ 改用 `sandbox=""` + `srcdoc` 的 iframe，与成员侧同一套隔离。
- **「算法影子模式」过期指引 / 影子面板每 15 秒重跑 7 天回放 / 反馈搜索每敲一键全量查库** → 分别修正指引、移出自动刷新、加 250ms 防抖。
- **文档与实现不符**：`用户限制说明` 的「不再保存图片文件、不提供下载」→ 与实际（生成记录开启时保存原图、可打包下载）对齐；RPM「10 次/分钟」→ 改为「自助领取 5、后台手建 10」；`SYSTEM-FACTS` 记录两条已知不闭合与新增校验。
- **落地页「多人共用会被拦截并回收」** → 「会被记录证据并回收 Key」（防分享当前是 observe，承诺要与处置方式一致）。

### 已核实为误报（不改，避免重复劳动）

- 「后台新建 Key 忽略 auto 选项」：UI 是先 POST 再用 `PATCH {quota:'auto'}` 补一次，后端 PATCH 正确处理。
- 「Anlas 模式 off/auto 不写 `anlas_auto`」：`PATCH` 里 `mode != "auto"` 时写 −1，语义正确。

### 仍需决定

1. **per-Key 功能白名单会被 Anlas 权限绕过**（`features.check` 里 `has_anlas` 提前 return）：这是 10-10 站长「放开 Anlas」的有意设计，但结果是「后台取消了 Vibe/放大/导演工具的勾选也拦不住有 Anlas 的 Key」。若要恢复白名单优先，把白名单判断提到 `ANLAS_FEATURES` 之前即可（3 行）。
2. **`GLOBAL_DAILY_ANLAS`（默认 200）没有后台入口**：默认值下 Vibe 实际是开放的，但没有任何地方显示或调整。
3. **`is_test` 语义**：注释与 SQL 不一致（注释说测试 Key 也照样应用，SQL 排除），已修注释方向但语义统一留待决定。
4. **邀请 Key 绑定绕过 `issue_hourly_cap`**：关闭注册豁免是有意的，但每小时限速也一起绕过了（那条限速正是为 Discord 风控加的），建议保留限速。

## 4. 日志与成员实际行为对应

### 已修

- **拒绝原因码补齐**：新增 `member_quota` / `site_quota` / `queue_timeout` / `key_rate` / `body_abort` / `feature_off` / `param`，按**线上真实文案**回填最近 2 天。实测近 2 天「空原因」从 **274 条降到 2 条**，分布变成 `paced` 1095 / `daily_cap` 552 / `over_base` 259 / `hourly_cap` 191 / `member_quota` 173 / `key_rate` 86 …
- **排队超时归入 `SITE_LEVEL`**：不再计入「单 Key 被拒 ≥60 → 暂停 1 小时」（忙时正常重试的成员不再被误判成客户端死循环）；个人额度用完**仍计入**（客户端无视 402 反复重试正是该规则要抓的）。
- **本地拒绝退还 Key 的 15 秒出图间隔**（站点级上限 / 冷却 / 排队满 / 熔断）：假上游端到端实测 #1 成功 → #2 等 15 秒撞上限 → **#3 立即返回（0.0s）**；修复前 #3 还要再等 15 秒。
- **删除测试 Key 不再让历史用量回流成员统计**：墓碑表 `deleted_key_usage_flags` 增加 `is_test`（含老库触发器重建），`NOT_TEST` 一并排除。
- **记账任务关停前排空**：`record()` 的 fire-and-forget 任务登记并在关库前 `wait`（最多 10 秒），失败时把 `key_id/kind/images` 写进 Bug 记录（部署窗口的「有图无账」空洞最难解释）。

### 未改（已知口径差异，建议站长知情）

1. **`总览今日张数` 含测试 / 已删除 Key**：页面已经分列「成员 X / 站长测试 Y」，但没有排除已删除 Key 的 counters（线上残留 4 行 / 13 张）。影响很小，未动。
2. **`status_hourly` 与 `usage_log` 不是同一批样本**：鉴权失败（401/404/405）只进状态码计数、进程重启会丢最多 5 分钟、流式记 200 而实际中途失败。两处并排放着容易被误读。
3. **`status='cancelled'` 是第四种状态**，各处口径不一（首页不计、后台算失败）。
4. **`usage_log_retention_days` 默认为 0（永久）**：一旦设置，依赖日志的指标（累计张数、7 天基线、重启补数）会静默缩水——建议在后台显示「当前保留期 / 最早日志时间」。
